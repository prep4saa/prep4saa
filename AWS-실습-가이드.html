시나리오 1 — Serverless REST API

일일 사용 횟수 제한 시스템 구축 (Firebase 대체)

🎯 목표

사용자별 일일 문제 생성 횟수를 제한하는 Serverless API를 구축합니다.

📐 아키텍처

[Client App] ↓ HTTPS [API Gateway: trade-api] GET /count/{userId} POST /count/{userId} ↓ AWS_PROXY [Lambda: trade-api-daily-count (Node.js 22)] ↓ AWS SDK [DynamoDB: user-daily-count] PK: userId (HASH) SK: date (RANGE) GSI: date-index TTL: 자정 자동 삭제

1️⃣ DynamoDB 설계

왜 DynamoDB?

항목이유
Key-Value 단순 구조userId당 1개 레코드 - 관계형 불필요
TTL 기능자정 자동 초기화 (cron job 불필요)
Auto-scaling트래픽 증가에 자동 대응
서버리스관리할 인프라 없음

핵심 명령어

# 테이블 생성 (PK + SK + GSI)
aws dynamodb create-table \
  --table-name user-daily-count \
  --attribute-definitions \
      AttributeName=userId,AttributeType=S \
      AttributeName=date,AttributeType=S \
  --key-schema \
      AttributeName=userId,KeyType=HASH \
      AttributeName=date,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST \
  --global-secondary-indexes '[{
      "IndexName": "date-index",
      "KeySchema": [{"AttributeName": "date", "KeyType": "HASH"}],
      "Projection": {"ProjectionType": "ALL"}
    }]' \
  --region us-east-1

# TTL 활성화
aws dynamodb update-time-to-live \
  --table-name user-daily-count \
  --time-to-live-specification "Enabled=true, AttributeName=ttl" \
  --region us-east-1

1️⃣ SQS 큐 + DLQ

왜 DLQ?

Lambda가 처리 실패 시 메시지가 무한 재시도되거나 사라지는 것을 방지. 3번 실패 시 DLQ에 보관 → 나중에 재처리 가능.

# 1. DLQ 먼저 생성 (메인 큐가 참조)
aws sqs create-queue \
  --queue-name problem-generation-dlq \
  --region us-east-1

# 2. DLQ ARN 조회
aws sqs get-queue-attributes \
  --queue-url  \
  --attribute-names QueueArn

# 3. 메인 큐 생성 (RedrivePolicy로 DLQ 연결)
aws sqs create-queue \
  --queue-name problem-generation-queue \
  --attributes '{
    "RedrivePolicy": "{\"deadLetterTargetArn\":\"\",\"maxReceiveCount\":\"3\"}"
  }'

시나리오 3 — RDS + ElastiCache + Bastion

3-tier VPC 아키텍처 + 캐싱 패턴 (진행 중)

🎯 목표

실무 표준인 3-tier VPC 안에 RDS PostgreSQL과 ElastiCache Redis를 배치하고, Cache Invalidation 패턴으로 통계 조회를 최적화합니다.

📐 전체 아키텍처

[로컬 PC / DBeaver] ↓ Session Manager Tunnel [VPC: 10.0.0.0/16] │ ├── [Public Subnet × 2 AZ] │ └── Bastion EC2 (점프 서버) │ ├── [Private App Subnet × 2 AZ] │ └── Lambda (saa-db-init) │ └── [Private Data Subnet × 2 AZ] ├── RDS PostgreSQL (saa-quiz-db) └── ElastiCache Redis (saa-quiz-cache) + Secrets Manager (DB 비밀번호 보관) + Security Groups × 4 (lambda, rds, redis, bastion) + IAM Roles × 2 (Lambda, Bastion) + VPC Endpoints × 2 (S3, DynamoDB - Gateway 무료)

1️⃣ VPC 설계 (3-tier)

TierCIDR용도인터넷 접근
Public10.0.1.0/24, 10.0.2.0/24ALB, Bastion인바운드 ✅ / 아웃바운드 ✅
Private App10.0.10.0/24, 10.0.11.0/24Lambda, ECS인바운드 ❌ / NAT or Endpoint
Private Data10.0.20.0/24, 10.0.21.0/24RDS, Redis인바운드 ❌ / 아웃바운드 ❌

왜 Tier 분리?

  • 보안 사고 시 피해 최소화
  • DB는 절대 인터넷에 노출되지 않게
  • Lambda가 해킹돼도 DB 직접 노출 안 됨
  • Multi-AZ로 한 AZ 장애 시에도 작동

2️⃣ Security Groups (보안 핵심)

SG ID 기반 인바운드 (CIDR 아님)

# RDS 보안그룹: Lambda SG에서만 5432 허용
resource "aws_security_group" "rds" {
  ingress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.lambda.id]  # SG ID로 제한
  }
}
인터뷰 포인트: "I used SG IDs instead of CIDR blocks for ingress rules. This way, even if the source IP changes, only resources with the specific SG can access the DB."

핵심 개념 정리

1. VPC 네트워킹

  • CIDR 블록: 10.0.0.0/16 = 65,536 IP
  • Subnet Tier: Public / Private App / Private Data 분리
  • Internet Gateway: Public Subnet의 인터넷 접근
  • VPC Endpoint: S3/DynamoDB Gateway = 무료, 다른 서비스는 Interface 유료

2. 보안 (Security)

  • Security Group: SG ID 기반 인바운드 (IP 무관)
  • IAM Role: EC2/Lambda에 권한 부여 (자격증명 X)
  • IAM Group: 정책 10개 한도 우회
  • Secrets Manager: 비번 자동 생성 + 안전 보관
  • Bastion + Session Manager: SSH 키 없이 안전 접근
  • 최소 권한 원칙: FullAccess 대신 커스텀 정책

3. 데이터베이스 패턴

  • RDS: 관계형 (PostgreSQL/MySQL)
  • DynamoDB: Key-Value NoSQL, PK + SK + GSI
  • ElastiCache: Redis 캐시
  • Multi-AZ: 고가용성
  • Encryption at Rest: KMS 자동 암호화

4. 컴퓨트

  • Lambda: Pay-per-execution, Auto-scaling
  • Lambda VPC 통합: ENI 자동 생성
  • EC2: Public Subnet + IGW 라우팅
  • IMDSv2: 메타데이터 서비스 보안 강화

5. 이벤트 드리븐 패턴

  • SQS: 메시지 큐, 버퍼 역할
  • DLQ: 실패 메시지 격리, 유실 방지
  • SNS: Pub/Sub, fan-out
  • RedrivePolicy: maxReceiveCount=3
  • Event Source Mapping: SQS → Lambda 자동 트리거

6. IaC (Terraform)

  • 모듈 분리: vpc/, rds/, elasticache/, bastion/
  • data 블록: 다른 모듈 리소스 참조
  • random_password: 시크릿 자동 생성
  • terraform state, plan, apply, destroy

인터뷰 답변 템플릿

전체 시스템 설명

"I designed and implemented a 3-tier VPC architecture using Terraform. RDS PostgreSQL and ElastiCache Redis sit in private data subnets, isolated from the internet. A Bastion EC2 with AWS Session Manager provides secure access without exposing SSH ports.

Database credentials are managed through Secrets Manager. Lambda functions run inside the VPC with security groups controlled by SG IDs rather than IP addresses, ensuring access remains scoped as the infrastructure evolves.

For the event-driven side, I implemented an SQS queue with a Dead Letter Queue for fault tolerance. When the AI API fails, the system queues an error message that triggers a Lambda function, which publishes to SNS for email alerting. This decouples error handling from the main request flow."

보안 답변

"I applied the principle of least privilege throughout. For Lambda's SQS access, I wrote a custom IAM policy with only ReceiveMessage, DeleteMessage on the specific queue ARN, instead of using AmazonSQSFullAccess. Database passwords are auto-generated by Terraform's random_password and stored in Secrets Manager — never hardcoded in code or environment variables in production."

네트워킹 답변

"Instead of opening port 22 on the bastion host, I used AWS Session Manager port forwarding. This eliminates SSH key management, keeps the bastion's inbound rules empty, and provides full audit trail through CloudTrail."

비용 최적화

"I used Gateway-type VPC Endpoints for S3 and DynamoDB instead of NAT Gateway, saving approximately $32/month per AZ. For Secrets Manager access from VPC Lambda, I evaluated Interface Endpoints (~$14/month) versus injecting credentials as environment variables at deploy time — chose the latter for cost while documenting the security tradeoff."
